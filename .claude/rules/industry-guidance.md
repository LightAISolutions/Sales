# Industry Guidance Command

If the user says **"industry guidance: <document>"** (or similar: "add this to Industry Guidance", "analyze this document for the guidance hub", "new guidance doc", or uploads an industry-wide document with that intent):

1. **Ingest the source** — copy the uploaded document to `repository-information/industry-guidance/sources/<slug>.pdf` (kebab-case slug with publisher + topic + date, e.g. `nvidia-800vdc-white-paper-2026-08.pdf`). Image-only PDFs are read visually with the Read tool's `pages` parameter (PyMuPDF `get_text()` returning 0 chars on every page identifies them)
2. **Deep-read and verify** — read every page; extract all quantitative claims and dated milestones with page references; verify the numbers with at least one independent re-extraction pass (subagents assigned page ranges) before any figure enters the content. Respect the source's reproduction notice: analysis is original prose, quantitative claims carry page citations, figures are re-expressed from stated data — never reproduced as images
3. **Write the analysis markdown** — `repository-information/industry-guidance/<slug>-analysis.md` (never deployed; the source of truth). Standard shape: what the document is → executive read → known-vs-new map tailored to the developer's current curriculum → per-topic deep dives with advantages/disadvantages made explicit → "what it means for <active engagement>" → claims ledger (page-referenced) → what the document does NOT say
4. **Author the in-app module** — a new `guidanceDoc<Name>_()` function in `googleAppsScripts/Classroom/Classroom.gs`, **below the `// CONTENT END` fence** (guidance is authored by a named `industry guidance:` session, never by the unattended C2 pipeline, so it must sit outside the pipeline's write set — `CLASSROOM-COMMITTER-CONTRACT.md` §3, enforced by `scripts/check-classroom-pipeline.py`), registered in `guidanceDocs_()` **with a `group` meta field and a `reviewBy` meta field** (see step 10) — the topic-lane label the library view groups by (current lanes: `Technology Foundations`, `The AI Data-Center Wave`, `Market Access & Bankability`; add a new lane only when no existing one fits). Keep `guidanceDocs_()` ordered by lane so the index arrives grouped; `guidanceIndex_()` emits `group` and `Classroom.html`'s library view renders a lane header whenever it changes (2026-08-29). The module JSON's section kinds (`prose`, `callout`, `table`, `proscons`, `timeline`, `bars`, `flashcards`, `quiz`, `ledger`) plus `glossary`, `tiles`, per-section `sales` notes (rendered under a "Sales angle" label; renamed from `zh` 2026-08-29) and `{{term}}` tooltips are rendered by `Classroom.html`'s `cl*` renderer — the same vocabulary lessons, briefings and reports use, so **new documents need no page changes**. Since C3 session 3 a module's sections are also **tickable** (`clProgressValid_` admits every registered module behind the `guidance` capability) and its `flashcards` / `quiz` sections **enter the C4 drill** as `gc:`/`gq:` items (`clDrillGuidanceItems_`) — both automatic, no authoring action needed. Timeline lane colors are the CVD-validated trio (gold `#b18f35` generations/core, blue `#4f83e6` deployment/milestones, rose `#cc5f75` ecosystem); re-run the dataviz validator if new chart colors are introduced. The library view carries a client-side **search** over every module's flattened section text and glossary (`clGuidanceFetchAll` caches all nine docs once per page load; hits open the module scrolled to the section) and a **unified glossary** view merging all modules' terms alphabetically with per-module definitions and source chips — both ride the existing role-gated ops, no authoring action needed. **Company-name chips are a Profiler-only behaviour and did not come across**: `gdLinkCompanies` walks Profiler's registry and rewrites text nodes, and Classroom has no equivalent, so covered company names inside module prose render as plain text here. Adding one would be a page-wide Classroom feature, not an authoring step — do not assume the chips when writing. **Content scope (developer directive 2026-08-29): modules give guidance to supplier/buyer groups only** ("BESS suppliers", "TRU/SST suppliers", "§154-listed suppliers", "developers", "integrators", "hyperscalers"…) — never to a single named company (statutory facts naming companies, like the NDAA §154(b) list, are fine as objective information). **One exception, developer-approved 2026-09-07 (`INTEGRATED-REMEDIATION-PLAN.md` §7.2 decision 2): the landscape modules** — `landscape-<segment-id>-YYYY-MM`, lane The Value Chain, specified in `CLASSROOM-CURRICULUM-PLAN.md` §10.6 — name and rank the segment's covered companies by construction, at the contributor tier, with every claim on a dossier in the claims ledger; they are the one module class that does, and the guidance they give is still to a group (the seller reading it). Company-specific analysis reaches admins **inside** modules via the **Admin lens**: a report's `guidanceOverlays[]` anchors (PROFILER-SCHEMA.md → Report schema) render 🔒 panels in the anchored sections for viewers with the `reports` capability only — never as module content. The lens re-hosted in Classroom at C3 session 2 (`clLoadAdminLens` / `clApplyAdminLens`, `clCan('reports')`, reading the same public `reports/*.report.json` off Pages); the reports themselves are still authored by the Profiler Report Command and still live under `live-site-pages/profiler-data/reports/`
5. **Access model** — the two browser-facing guidance ops (`action=guidance`, `gop=index|doc`) are **gated server-side** in `Classroom.gs`'s `handleGuidanceOp_` by a single `clRequire_(sess, 'guidance', …)` call: the `guidance` capability in **`CL_ROLE_CAPS`** — admin and contributor — which throws `CLASSROOM_FORBIDDEN` (surfacing as `ROLE_DENIED`) for analyst, viewer and any unknown role, and audits the denial. The page's own `clCan('guidance')` decides whether the masthead link and the `#guidance` routes render at all; that is UI convenience, and `clRequire_` is the boundary. Those are the same tiers `GUIDANCE_ROLES` admitted in Profiler — **the gate followed the content across apps** — so keep `CL_ROLE_CAPS.guidance` and Profiler's `GUIDANCE_ROLES` in sync while Profiler still gates its link (see the Role + Access matrix in `.claude/rules/profiler-app.md`). Module content ships inside `Classroom.gs` — repo + GAS project only, never on public Pages. **`gop=mentions` is NOT a third browser op.** `guidanceMentions_()` lives in `Classroom.gs` because it scans the module JSON, and it answers only on `?action=guidancepeer&t=…&gpop=mentions` — a **token-gated peer route** (the `GUIDANCE_PEER_TOKEN` Script Property, set to the same value in both projects, refused flat while unset, no default in code — the mirror of `scHandleCorpus_` in `Scraper.gs`). Its only consumer is Profiler, whose `handleGuidanceOp_`'s `gop=mentions` branch relays it server-to-server via `guidanceMentionsProxy_()`; `guidanceAllowed_` on the Profiler side is still the single browser-facing boundary deciding who may ask. The answer feeds the dossier's "Covered in guidance modules" chips, which deep-link to `Classroom.html#guidance/<id>`
6. **Versioning** — content-only additions bump the **Classroom GAS** version ([PC-GS-VERSION] #1) since the module lives in `Classroom.gs` (`Classroom.gs` `VERSION` **and** `live-site-pages/gs-versions/Classroomgs.version.txt`, together in one commit); renderer/UI changes also bump the **Classroom page** version and its `<meta build-version>` ([PC-HTML-VERSION] #2). The changelogs are Classroom's — `live-site-pages/gs-changelogs/Classroomgs.changelog.md` and, for renderer work, `live-site-pages/html-changelogs/Classroomhtml.changelog.md`. Standard Pre-Commit checklist applies; public page/GAS changelog entries stay generic ("guidance library updated") per changelog-security — never name the analyzed document publicly. **Profiler is not touched by module authoring any more** — if a change makes you edit `Profiler.gs` or `Profiler.html`, stop and re-read what you are doing
7. **Verify before push** — `node --check` on a `.js` copy of `Classroom.gs`, `scripts/check-gas-inner-scripts.js`, `scripts/check-classroom-content.py` (it runs the gate truth table, which now counts the registered modules and asserts lesson ids and module ids stay disjoint) and `scripts/check-classroom-curriculum.py --strict`, plus a Playwright render of the new module at `Classroom.html#guidance/<id>` with **zero page errors**. Render recipe: serve a scratch copy over `http://127.0.0.1` with `_e = ''` and `AUTO_REFRESH = false`, seed the session **after** page load (`HTML_CONFIG.STORAGE_TYPE` is `sessionStorage` and the single-tab enforcement clears it on load), override `window._gasPost` **after** load too (it is a top-level `function` declaration, so an init-script assignment is overwritten), hide `#auth-wall` / `.splash` / `#gas-pill` / `#verify-overlay`, then `clHeaderShow(); clAppMount();`
8. **Refreshes** — a revised edition of a covered document updates the same module (bump its `updated` field), archives nothing (git history suffices), and amends any engagement docs the findings touch (e.g. the Zhonhen study-prep set), regenerating affected study-prep PDFs
9. **Scraper interest seed (authoring-time sync)** — the Scraper↔Profiler interest model syncs guidance topics at authoring time, not via a runtime probe (developer decision 2026-08-27): when registering a new guidance module, also add a matching topic seed to `SCRAPER_INTEREST_TOPIC_SEEDS` in `googleAppsScripts/Scraper/Scraper.gs` — `key: 'topic-<slug>'`, `label`, default search `terms`, `source: 'guidance:<module-id>'`. Scraper's daily registry sync upserts the seed into its Interests tab (default-ON, flagged "New topic") and the digest rubric scores against it. This touches `Scraper.gs`, so bump the Scraper GAS version too ([PC-GS-VERSION] #1)

10. **Freshness discipline (2026-08-29)** — every module carries a `reviewBy: "YYYY-MM-DD"` meta field, set at authoring from the module's **own nearest dated gate** (a regulatory effective date, a deployment milestone, a rate that changes on a schedule) rather than a fixed cadence; slow-moving fundamentals modules default to ~6 months from `updated`. `guidanceIndex_()` emits it, and `Classroom.html` renders it as a chip on the library cards and the module header (`clReviewChip`: plain >30 days out, gold within 30 days, red "⚠ review due" once passed); `scripts/check-classroom-curriculum.py` also lists modules inside a 30-day horizon. Reports age independently: the report library and report view show an age chip from the report's date on the dossier freshness tiers — fresh ≤45d / aging ≤120d / stale (`rpAgeChip`); superseded reports get no chip. **The quarterly review Routine** — `Industry Guidance quarterly review` (`trig_01CrhxzfBV6uKQNKpUXLLMSZ`, cron `0 13 15 1,4,7,10 *`, fresh session per fire; armed 2026-08-29, **prompt re-targeted at `Classroom.gs` in place at C3 session 3 with the developer's explicit approval** — same trigger id, same cron, run history intact; never delete-and-recreate it) — walks the modules returned by `guidanceDocs_()` in `googleAppsScripts/Classroom/Classroom.gs`, re-verifies each module's dated gates against primary sources, updates stale content (content-scope rule intact), refreshes `updated`/`reviewBy`, bumps the **Classroom** GAS version and changelog, and — for the report half, which is still Profiler's — validates report overlay anchors via `check-profiler-reports.py` and recommends superseding aged reports. When a module revision changes its dated gates mid-quarter, set the new `reviewBy` in the same commit — the Routine is the backstop, not the primary mechanism

**Q&A channels are deliberately v1-absent** (developer decision 2026-08-22). If revisited: `anthropicSummarize_` in Profiler.gs is the existing Claude API precedent (Script Properties `ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL`) — read the `claude-api` skill before extending it.
